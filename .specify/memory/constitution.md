## Core Principles

### I. Spec-Driven Development First

Every feature, component, and architectural decision MUST originate from a written Markdown specification. All implementation is generated by Claude Code from refined specs.

**Rationale**: Ensures all development is intentional, documented, and traceable. Eliminates ad-hoc coding and ensures every code change has a documented purpose and design rationale.

**Non-negotiable rules**:
- No code generation without a corresponding spec.md
- Specifications MUST be complete before implementation begins
- All changes MUST trace back to a specification document
- Every feature MUST have its own Markdown spec file

### II. No Manual Coding Allowed

Participants MUST never write or edit production code manually. All code is generated by Claude Code. Any deviation disqualifies the submission for that phase.

**Rationale**: Validates the effectiveness of AI-assisted development and spec-driven methodology. Ensures consistent code quality and adherence to architectural patterns.

**Non-negotiable rules**:
- Human intervention limited to specification writing and refinement
- All production code MUST be generated by Claude Code
- Manual edits result in phase disqualification
- Refinement happens only through spec improvement and re-generation

### III. Iterative Refinement

Specifications MUST be iteratively clarified and refined until Claude Code produces correct, clean, and functional output.

**Rationale**: Acknowledges that perfect specifications are rare on first attempt. Encourages learning and improvement through feedback cycles.

**Non-negotiable rules**:
- Accept that initial specs may be incomplete or ambiguous
- Use Claude Code output as validation of spec quality
- Iterate spec → generate → validate → refine until success
- Document all iterations in specs history folder

### IV. Agentic Dev Stack Workflow

Strictly follow the workflow: Write spec → Generate plan → Break into tasks → Implement via Claude Code → Validate → Iterate.

**Rationale**: Provides a structured, repeatable process that ensures quality at each stage and enables early detection of issues.

**Non-negotiable rules**:
- Follow workflow phases in order: `/sp.specify` → `/sp.plan` → `/sp.tasks` → `/sp.implement`
- Do not skip phases
- Complete validation before proceeding to next phase
- All workflows MUST be documented in repository

### V. Clean Code & Professional Standards

All generated code MUST adhere to PEP8 (for Python), use type hints, be modular, readable, and follow separation of concerns (UI, logic, storage, etc.).

**Rationale**: Ensures maintainability, readability, and professional quality suitable for production systems.

**Non-negotiable rules**:
- Python code MUST comply with PEP8
- All functions and methods MUST have type hints
- Code MUST be organized by concerns (models, services, CLI, storage)
- No monolithic files; enforce modular design
- Generated code MUST be clean, typed, and follow best practices

### VI. Transparency & Auditability

The entire development process (specs, plans, tasks, iterations, prompts) MUST be preserved in the repository for judging.

**Rationale**: Enables learning, reproduction, and fair evaluation. Demonstrates the complete journey from idea to implementation. Judges can trace every line of code back to a spec, plan, and Claude Code generation step.

**Non-negotiable rules**:
- All specs, plans, and tasks stored in `specs/` directory
- All prompts recorded as PHRs in `history/prompts/` directory
- All ADRs stored in `history/adr/` directory
- Git history MUST show clear progression through phases
- CLAUDE.md files document all AI interactions and instructions
- Constitution and high-level architecture specs MUST be maintained and updated across phases

## Key Standards

### Project Structure

**Monorepo Organization**:
- `.specify/` or `.spec-kit/` - SpecKit Plus templates, scripts, and configuration
- `specs/` - All specifications organized by type
- `history/prompts/` - Prompt History Records (PHRs) organized by stage and feature
- `history/adr/` - Architecture Decision Records
- `frontend/`, `backend/`, `src/` - Source code (structure depends on phase)
- `CLAUDE.md` - Root-level AI instructions and prompts
- `README.md` - Clear setup and run instructions

**Specs History Requirement**:
- Every phase MUST include complete specs showing evolution
- Track iterations through git commits
- Maintain clear version history

**Documentation Requirement**:
- CLAUDE.md at root and subdirectories documenting all Claude instructions
- README.md with setup, run, and validation instructions
- Every feature MUST have its own Markdown spec file
- Specs MUST include acceptance criteria and test scenarios

### Feature Implementation

**Phase I-V Feature Coverage**:
- Phase I–V MUST implement all Basic Level features (Add, Delete, Update, View, Mark Complete)
- Later phases progressively add Intermediate and Advanced features as capacity allows
- Phases III–V MUST include a fully functional natural-language AI chatbot capable of managing todos (e.g., "Reschedule my morning meetings to 2 PM")
- Code MUST be fully typed
- Code MUST be modular and follow best practices
- Each phase builds on previous phases

**Quality Gates**:
- Phase I: Python 3.13+, UV, in-memory storage only - console app with CRUD operations
- Phase II: Next.js 16+ (App Router), FastAPI, file-based persistence
- Phase III: Natural language chatbot interface with intelligent command interpretation
- Phase IV: Docker, Minikube, Helm, kubectl-ai, kagent - local Kubernetes deployment
- Phase V: Kafka, Dapr, DigitalOcean Kubernetes (DOKS) - production deployment with event-driven architecture

### Technology Compliance

**Phase I Requirements**:
- Python 3.13+ MUST be used
- UV package manager MUST be used
- In-memory storage only (no persistence)
- Console-based interface

**Phase II Requirements**:
- Next.js 16+ with App Router MUST be used for frontend
- FastAPI MUST be used for backend
- File-based persistence added
- Full-stack web application

**Phase III Requirements**:
- Natural language AI chatbot interface
- Intelligent command interpretation (not just keyword matching)
- Examples: "Add buy milk to my todo list", "Show me incomplete tasks", "Mark task 3 as done"

**Phase IV Requirements**:
- Docker containerization
- Minikube for local Kubernetes
- Helm charts for deployment
- kubectl-ai and kagent integration
- Container images built and deployed
- Services exposed and accessible
- Health checks passing

**Phase V Requirements**:
- Kafka for event streaming
- Dapr for distributed application runtime
- DigitalOcean Kubernetes (DOKS) for production deployment
- Event-driven components implemented
- Monitoring and observability configured
- Production-ready configuration (secrets, resource limits, etc.)

### AI Agent Capability

By Phase III, the chatbot MUST intelligently interpret and execute natural-language todo commands:
- Natural language understanding, not just keyword matching
- Context-aware command interpretation
- Intelligent error handling and user feedback
- Examples: "Reschedule my morning meetings to 2 PM", "What's on my plate today?", "Clear completed tasks"

## Governance

### Authority & Precedence

This Constitution serves as the immutable guiding document for the entire Hackathon II project. All decisions, specifications, and implementations MUST align with these principles.

In case of conflict:
1. Constitution principles take precedence over all other documents
2. Project-specific requirements (from hackathon brief) take precedence over general best practices
3. Documented architectural decisions (ADRs) take precedence over undocumented preferences

### Amendment Process

**Minor Amendments** (PATCH version - typos, clarifications, wording improvements):
- Can be made directly with git commit documenting change
- Increment PATCH version (e.g., 1.0.0 → 1.0.1)
- Update Last Amended date
- No template updates required

**Significant Amendments** (MINOR version - new sections, expanded guidance):
- Require documented justification
- Should create ADR documenting the decision
- Must update affected templates
- Increment MINOR version (e.g., 1.0.0 → 1.1.0)
- Update Last Amended date

**Breaking Amendments** (MAJOR version - principle removals, redefinitions, governance changes):
- Require documented justification and team consensus
- MUST create ADR documenting the decision
- MUST update all dependent templates
- Increment MAJOR version (e.g., 1.0.0 → 2.0.0)
- Update Last Amended date
- Notify all team members

### Compliance & Enforcement

**All phases MUST verify compliance**:
- Constitution check in plan.md validates principles
- Complexity tracking table documents any justified violations
- Simple alternatives MUST be rejected with documented rationale

**Automatic Disqualification Triggers**:
- Manual code edits to production code
- Missing or incomplete specs for implemented features
- Workflow phases skipped
- Missing required documentation artifacts

### Versioning Policy

**Format**: MAJOR.MINOR.PATCH
- **MAJOR**: Breaking changes to principles, removed principles, governance changes
- **MINOR**: New principles added, significant expansions to existing principles, new sections
- **PATCH**: Clarifications, typos, wording improvements, formatting
